# Architecture

## Request path

```text
Browser
  -> public static landing page
  -> protected workspace route
     -> Cloudflare Access
     -> Worker
        -> protected API request
        -> verified Access identity
        -> opaque subject-digest rate limit
        -> exact route and method preflight
        -> D1 invited user and active memberships
        -> workspace-scoped API response
  -> Static Assets binding for the React application
```

The Worker handles `/api/*` and each protected workspace parent/deep route before falling back to the built Vite application. Static Assets use single-page-application fallback. The `/` route is a static product introduction and makes no session request. Navigation to `/dashboard` is a full-page request so the configured Access application can perform its browser login flow before the Worker independently validates the JWT and active D1 membership, then serves the private React shell with `private, no-store` caching. An exact route-policy table keeps the public health endpoint separate from protected APIs. For every other API request, Access verification and subject-keyed rate limiting occur before route preflight; an unknown path or disallowed method then fails without a membership query, request-body read, R2 operation or Workflow call. This order preserves the protected boundary without spending workspace database work on a request that cannot be dispatched.

## Authentication and tenancy

The Worker validates the Access assertion against the configured issuer and a bounded allowlist of application audiences. A single audience remains the default; deployments that must split the documented private paths across multiple Access applications may store a comma-separated secret allowlist without publishing any audience value. The assertion is capped at 16 KiB before signature verification. After verification, only an identity-based application token with a control-character-free subject, email and optional display name inside the 256, 254 and 128 character limits can continue; email syntax is also checked. Invalid claims fail before Rate Limiting or D1 and are never echoed. Before protected D1 work, the Worker derives a fixed-length, versioned SHA-256 rate-limit key from a domain-separated verified subject. Replays and concurrent requests for that subject share the same approximate per-location counter, while the raw subject is not passed to the binding. It then resolves the active D1 user by bound subject or, for the first login only, by a verified invited email. Subject binding uses a conditional update that rechecks the active user, selected workspace and membership at the write boundary. A zero-row result re-reads both the subject winner and active membership: a different subject fails as a binding conflict, while revoked access leaves the subject unbound. Once bound, workspace resolution is read-only: headers scope the current request but never update `last_workspace_id`. An explicit fixed-URL `PUT /api/session/workspace` is the only switch path; it repeats the bound-subject, active-user, workspace and membership checks at its D1 write boundary before persisting the preference. While that request is pending, the React session state machine keeps the previous authenticated session and disables another selection, so protected children continue to receive only the previous workspace ID. It adopts the response only when its selected workspace matches the requested target, then remounts the routed workspace subtree under a non-rendered workspace key so an older asynchronous component state cannot flow into the new scope. A target-only denial, mismatched response or transient failure retains the previous scope and exposes bilingual retry/dismiss actions without showing the stable error code; Access expiry, invite removal or an identity-binding conflict clears the stale session and returns to the login gate.

A requested workspace header never grants access by itself. The selected workspace must be present in the caller's active membership set.

The protected workspace-member surface is available only to owner/admin roles. `GET` and `POST /api/workspace/members` list a directory in immutable member-ID order with at most 100 records per page, or create membership for a new invited identity or an existing active identity. The UI re-sorts only its already protected accumulated projection for readable active/email grouping. A private next-page member ID is returned in the protected body and replayed only through a bounded header on the fixed list URL; URL, malformed, unknown and cross-workspace cursors are rejected. Omitting the header requests the first page. `PATCH /api/workspace/member` likewise carries the private member target only in a bounded header. Invitations and membership/audit statements use one D1 batch, but never modify Cloudflare Access policy or rewrite an existing subject; deployment administrators maintain the matching exact-email Allow list separately. Updates use an expected membership version, reject self-management and admin escalation, and rely on D1 triggers to preserve at least one active owner across update or delete paths. The first verified Access login activates and binds a new invited user only while the membership is still active.

The owner/admin activity surface reads the existing append-only `audit_events` index without creating another event. `GET /api/workspace/activity` applies the resolved workspace as its first predicate, selects at most 51 rows to produce a 50-item page, and joins only the actor display name. Its public projection normalizes known action names and discards the event ID, target, request ID and metadata; an invalid legacy display name becomes the generic system actor. The private seek cursor is returned separately from activity items, kept in component memory and replayed only through a bounded fixed header. A cursor is looked up inside the same workspace before the older-page query, so a foreign or fabricated value fails without widening the data scope.

The public login route uses one typed Traditional-Chinese-first contract for its introduction, identity and membership boundaries, all recovery/navigation actions and fail-closed footer. A requested `next` value is reduced to `/dashboard`, `/catalogue`, `/asset-review` or `/builder`; dynamic path segments, queries and fragments are discarded before a generic bilingual destination name or same-origin top-level navigation is rendered. The five login-reason states remain separately typed. The page may probe the protected session endpoint only to redirect an already valid session; a denied or unavailable result renders bounded copy and no merchant record or identifier. The UI contract does not replace Worker authentication.

All browser API requests include `X-Requested-With: XMLHttpRequest`, allowing Access to return a bounded `401` when an application session expires. The client then requires a top-level re-login navigation. Logout uses Cloudflare Access's same-origin `/cdn-cgi/access/logout` endpoint; the application does not create a parallel session or identity bypass.

Every public API error crosses one shared response boundary with a stable code, a generated request ID and a message containing Traditional Chinese followed by English. The error constructor rejects single-language public copy. Request-body, catalogue, CSV／TSV, rate-limit and asset-file validation use the same contract; detailed GLB validator diagnostics are reduced to a stable validation code and a bounded bilingual category message. The browser splits that message only where the interface has separate language fields and uses safe bilingual fallback copy when an upstream response is malformed. Raw exceptions, parser labels and private record identifiers remain outside the response.

Owner provisioning is an out-of-band private operation. The tracked tool reads the exact login identity only from a private environment, writes a short-lived mode-`0600` SQL file, executes it through Wrangler against the configured D1 binding, verifies only a boolean owner result and removes the temporary file. It never returns the identity, private SQL or deployment coordinates.

## Storage bindings

D1 stores identity, workspace metadata, workspace-scoped catalogue records, private-file metadata, current asset review state, append-only review events, generation jobs/events, generation credit entitlements, provider-attempt state and persistent build selections. Catalogue, asset, generation and build mutations use expected versions or idempotency keys and write their state transition and minimal audit event through D1 batches.

The R2 binding stores up to four validated source views and one self-contained GLB model per asset under opaque, per-write keys. Before either Catalogue or Asset Review sends a file, one browser helper reconciles the local extension, browser MIME and complete bytes. Empty or `application/octet-stream` metadata is normalized only when a recognized extension and content establish the canonical type; conflicts fail before fetch, and the local filename is never transmitted. This preflight improves compatibility and feedback without widening trust: the Worker independently materializes a source upload within 10 MiB and checks matching canonical MIME, a static canvas of at most 8,192 px per edge and 24 MP, and complete container structure: PNG ordering and per-chunk CRC, JPEG frame/scan marker bounds, or still-WebP RIFF/chunk bounds. APNG and animated WebP are rejected before storage. The canonical `front` metadata remains on `product_assets`; `back`, `left` and `three-quarter` metadata uses a workspace-and-asset-scoped table whose constraints and triggers reject unknown views or inactive catalogue relationships. Manual and generated GLBs share one policy for exact container bounds, self-containment, buffer／bufferView／accessor ranges, triangle primitives, node graphs, effective dimensions, texture count and texture bytes. Each Worker upload then supplies the already computed SHA-256 to R2, which checks the received object and retains the digest metadata. Protected reads require size, MIME and checksum agreement with D1; the normal path can keep streaming when R2 SHA-256 metadata matches, while an older object without that metadata is materialized only within its 10/25 MiB bound, validated and rehashed. The browser wraps every returned private Blob in an abort-bound object-URL lease: cancellation before materialization creates no URL, while a later abort or component cleanup revokes an existing URL exactly once. This prevents a late response from extending the previous workspace or asset's in-memory file lifetime. Rollback, selected-view replacement, exact removal and Workflow compensation delete only one recorded key and retry one transient failure. Removal first commits guarded metadata, review reset, audit and generation-credit compensation in D1; rejected, stale or raced mutations never reach R2 deletion. A second delete failure remains best-effort: the inactive object stays private instead of reversing an already committed D1 transition. Objects are readable only through Access- and workspace-protected Worker routes; no bucket or permanent object URL is public. The Workflow binding can run the zero-cost synthetic validation pipeline when an explicitly controlled environment selects simulation mode. Only canonical `front` is eligible for that input boundary; additional views remain manual evidence. Tracked production configuration remains disabled, and the current Workflow performs no external provider or Workers AI call.

## Dashboard

The dashboard performs workspace-scoped aggregate reads only. Catalogue and asset counts are derived by bounded SQL queries. Compatibility readiness is evaluated from at most the latest 50 active build drafts and their selected catalogue records; the response returns at most six recent work items. Every work item carries separately bounded Traditional Chinese and English detail and status fields for asset review, export-ready and build-attention states. The client adds deterministic bilingual relative-time copy and uses one typed copy module for its page heading, primary actions, four metric summaries, queue count, readiness labels and empty/complete/incomplete readiness guidance. Dynamic English counts handle singular and plural forms without changing the authoritative numerical value. Both languages remain visible at desktop widths; the 390 px queue retains an accessible icon-led status and all other copy can wrap without page-level overflow. Asset-review work uses the fixed `/asset-review` path and passes its protected target only through a workspace-bound, in-memory React context that is cleared after the review page captures it. The target is not written to the URL, history state or persistent browser storage, and modified-link navigation safely opens the generic queue. Legacy query strings and fragments are ignored as targets and replaced with the clean route. The dashboard never creates a draft, appends an audit row or returns user identity.

## Catalogue and asset review

Catalogue reads are bounded to 100 rows per request and use an ID cursor returned only in the protected, non-cacheable JSON response. The browser retains it transiently and sends it in `X-RigStage-Catalogue-Cursor`; the Worker rejects URL query cursors and validates the header before D1 access. A selected private part ID is likewise sent only in `X-RigStage-Catalogue-Part-Id` to fixed mutation and source-creation endpoints, never in their URL, body or route log. The role and target are checked before either request body or storage access. Both cursor and target can operate only inside the resolved workspace because the verified request context supplies the workspace predicate. Staff, admin and owner roles may create, update or logically archive catalogue records; viewers remain read-only. Updates use optimistic record versions. CSV and TSV use one shared ordered-header/schema parser, validate at most 50 rows, and submit all catalogue and audit statements in one transactional D1 batch. The browser first performs the same complete parse after checking the 256 KiB limit and recognized extension/media-type agreement; the Worker independently accepts only exact registered media types and remains authoritative. Catalogue archive also checks for any reserved generation entitlement in its conditional update, so it cannot hide an in-progress or `awaiting_review` asset while leaving credit reserved. A database trigger independently protects the terminal `awaiting_review` case; after approval, rejection or terminal failure resolves the entitlement, the unchanged catalogue version can be archived normally. The client-provided workspace header never becomes a database scope directly; the verified request context supplies the workspace predicate. The Catalogue list uses one typed Traditional-Chinese-first presentation contract for page actions, filters, columns, all nine categories, every stock/asset/quality enum and dynamic stock counts. English counts handle singular and plural, unknown stock remains explicitly unverified, viewer write controls stay disabled and visible row copy omits private part and asset IDs. The Catalogue editor adds a dedicated typed contract for create, edit and view headings, every field, verification choice, guidance and operation stage while reusing the list's exhaustive category and stock maps. Its read-only projection disables all fields and omits mutation controls; visible context contains SKU and record version but no private part or asset ID. Bilingual labels and actions wrap at phone width. A separate module-level bilingual status contract covers list reads, product writes, two-step archive, source-asset creation, CSV／TSV template download and tabular import. Explicit info/success/warning/error tones drive the icon, colour and `status` or `alert` semantics. Valid bilingual public API messages may pass through, but monolingual network/parser errors use operation-specific fallback copy; because a lost response can follow a committed write, the fallback says the result is unconfirmed and requires a reload before retry rather than claiming no server state changed.

The review queue returns only draft or in-review assets whose catalogue part is active in the resolved workspace. Each D1 read returns at most 50 records plus one look-ahead row, ordered by `updated_at` and asset ID. A stable composite ordering marker and asset ID are encoded into a bounded response cursor; the client returns it only in `X-RigStage-Asset-Review-Cursor`, never in the URL. Before seeking, the Worker confirms that the cursor asset belongs to the resolved workspace. The encoded ordering marker remains the page boundary if that asset is later reviewed or reordered, so the same continuation is retryable; the cursor is not an authorization mechanism. The browser appends and deduplicates loaded records, derives the current position instead of storing a second count, aborts stale page requests, preserves the current record on failure and disables switching while form changes or an operation are pending. A selected asset ID is retained in component memory and sent only in `X-RigStage-Asset-Id` to the fixed detail and review endpoints; it is absent from their URL, body and route log. Viewer roles are rejected before a review target, body, D1 query or R2 object is read; a write-capable role must then provide a bounded target before body or storage access. The resolved workspace remains the first asset predicate. Staff may save drafts, and owner or admin roles may approve or reject. Approval requires a stored GLB model, the complete fixed checklist and three positive, bounded dimensions. The safe API projection always contains four source slots with only content type and size for available files; it never contains an object key or checksum. The client renders the shared domain checklist in its canonical order through an exhaustive Traditional-Chinese-first bilingual map; the three dimension keys use a typed bilingual list, and progress copy handles English singular/plural without altering the authoritative count. A dedicated module also exhaustively maps every review-status, source-kind and quality enum, then derives bilingual version and loaded-queue context without claiming an unavailable total. The header and metadata inspector consume that contract without rendering the protected asset ID. A separate typed source-image contract covers four selectable view labels, authorized/missing state, private preview alternative text, actionable missing-view accessibility names and confirmed/missing usage-rights evidence. Its UI state is derived from the editable review form but never replaces the persisted evidence checked by the Worker. At the approval boundary, the Worker bounds and reads the R2 model, repeats structural/self-contained GLB validation and compares SHA-256 with D1; matching size and MIME alone are insufficient. Database triggers also recheck the active catalogue relationship at every asset update and additional-view insert/update, so an archive that wins before the review batch causes the review, source-view metadata, audit and generation-accounting statements to roll back together. A failed state or integrity check changes no review, audit or generation-credit state. Visual geometry remains non-authoritative for compatibility. The review header consumes a module-level Traditional-Chinese-first status contract whose info/success/warning/error tone drives its icon, colour and `status` or `alert` announcement. Save, approve, reject, selected-view/model upload, exact selected-file removal and simulated-generation fallbacks distinguish each operation. Rejection is armed for one workspace-and-asset-version key on the first press and submitted only on the second; changing the form, file, generation request, workspace or asset version disarms it. The warning explains that rejection can release reserved credit but does not delete private files. Removal has a separate workspace, asset-version, kind and view key: its first press sends no request, switching views or starting another operation disarms it, and its second press removes only the still-selected file. These are accidental-action guards, while the Worker remains authoritative for role, scope, version and state. Valid bilingual API or file-validation messages may remain visible; a monolingual or unknown exception is treated as an ambiguous result and asks for a reload before retrying rather than asserting that the server write, upload, removal or idempotent job did not occur.

Catalogue staff create an asset by uploading its validated canonical `front` source image. Private file reads, replacements and removals use one fixed API URL with bounded `X-RigStage-Asset-Id` and `X-RigStage-Asset-File-Kind` headers; source requests also use the enumerated `X-RigStage-Asset-Source-View` header, with a missing header defaulting to `front` only for backward compatibility. A source-view header on a model request fails before storage work. The asset ID is absent from the URL, binary body and route log, and removal has no body. Viewer mutations fail before target, body, D1 or R2 as applicable, while an authorized read validates every target before the workspace-first D1 lookup or R2 access. File replacement uses an expected review version, stores a new R2 object, then commits selected-view/model metadata and a minimal audit event only while the catalogue part is still active. File removal uses the same version and active-catalogue guards, commits exact metadata removal, review reset, audit and reserved-generation compensation in one D1 batch, then deletes only the previously selected object key. If a concurrent archive or file change wins, the complete transition rolls back and no existing object is deleted. Replacement or removal resets the checklist, source-rights confirmation, dimensions and approval state while every other private file remains unchanged. The review UI presents four selectable source views plus GLB requirements, upload/replace/remove/progress actions, two-step removal confirmation and the Access boundary through one Traditional-Chinese-first bilingual copy contract. The viewport keeps its four canonical camera values separate from their exhaustive bilingual labels and uses one typed copy contract for tool accessibility names, camera readout, authorized/missing model states and the non-compatibility disclaimer. The shared Three.js preview adds generic bilingual canvas, loading and decode-failure text without surfacing parser details. Three.js and GLB parsing remain lazy-loaded only when an authorized model blob is available.

## Generation jobs

Generation reads and requests use one fixed API URL and `X-RigStage-Asset-Id`; the selected asset ID stays in component memory and is absent from the URL, JSON body and route log. Any active member may read status. Only an owner or admin may request generation for a current, unapproved asset whose active catalogue part, canonical private `front` source image and saved rights confirmation belong to the resolved workspace. Additional source views are manual-review evidence only and are not read or described to the provider boundary. Role denial precedes target or body reads, and the bounded target is validated before capability, idempotency, body, D1, R2 or Workflow work. The API requires an `Idempotency-Key` and an available non-monetary generation credit. The browser holds at most one key in component memory and reuses it only when the same workspace, asset and requested review version has an ambiguous network, parsing or server result; a confirmed response releases it, while a changed input rotates it. The key is never placed in a URL or persistent browser storage. A server replay is valid only when both the asset and requested review version match the stored job; an input mismatch fails before Workflow or credit activity. The route rechecks the canonical source R2 object's size, content type and SHA-256 against D1 before any reservation. One D1 batch then moves a unit from available to reserved, inserts the job and entitlement, and appends the reserve, job and audit events before creating a uniquely identified Workflow instance. A database trigger rechecks the active catalogue state, asset version, canonical source checksum, rights confirmation and unapproved status at job insertion; a concurrent archive or asset change aborts and rolls back that complete batch. A guarded query prevents another job while the asset has a queued, running, validating or `awaiting_review` job with a reserved entitlement.

Cancellation reuses the fixed URL with bodyless `DELETE` and adds one bounded protected job header. The UI requires a second activation for the same workspace, asset version and queued job, but the Worker is authoritative: only `queued` may atomically become `cancelled`, append its event/audit and release one reservation. If Workflow changes the state to `running` first, the update changes nothing and returns a conflict without stopping processing or releasing credit. If cancellation wins, a later Workflow claim returns `cancelled` before source or provider work. Replays make no additional accounting or audit change.

The current provider-neutral adapter supports only zero-cost simulation. It receives stable pseudonymous workspace, job and attempt references, a source MIME/size/SHA-256 descriptor and explicit output limits; it does not receive a raw workspace ID, private object key or permanent URL. A D1 provider-attempt row makes terminal results immutable and distinguishes duplicate, conflicting, late and out-of-order results.

Each Workflow side effect lives inside a named, bounded, retryable step: claim the unchanged input, active catalogue state and reserved entitlement, recheck private source existence/size/content type/SHA-256, begin the attempt, create a runtime synthetic GLB, enforce the provider cost-unit cap, validate before storage, privately write the deterministic R2 draft with its checksum, move the job to validation, read the object back, repeat strict validation and compare its checksum. A missing or drifted source at this second boundary fails before a provider attempt and releases the reservation once. A catalogue archive before claim records `GENERATION_INPUT_STALE` without a provider attempt; the final staging statement rechecks active catalogue state again, removes a late private draft and releases once if an archive wins that commit race. Strict output validation covers GLB/chunk bounds, glTF 2.0 declarations, embedded resources, buffer/accessor ranges, triangle primitives, nested node scale, geometry dimensions, triangle count, texture count and texture bytes. A conditional D1 batch then replaces the draft model metadata, increments the asset review version, resets all approval evidence and marks the job `awaiting_review`. Superseded private output enters a separate idempotent cleanup step whose exact-key delete also receives the single bounded retry.

The customer-facing credit remains reserved while the draft awaits a human decision. Approval settles it. Queued cancellation, rejection, terminal failure, Workflow-start failure or replacement of the generated draft releases it once. Provider cost units and customer credit units are separate bounded integer ledgers; neither is a price, payment balance or claim that a billable provider ran. The Asset Review inspector renders the complete mode, job-status and entitlement enums through exhaustive Traditional-Chinese-first bilingual mappings. Available/reserved and settled/released counts explicitly use a non-monetary credit label; absent job, entitlement, cost and validation values have readable bilingual states instead of an unexplained dash. Its bounded recent history re-filters the response against the current asset, preserves server order, caps rendering at 20 and formats timestamps in Hong Kong time; it uses job IDs only as non-rendered React keys and omits diagnostic codes. A stable bounded validation code remains unchanged for diagnosis in the latest-job technical summary.

Any source replacement, review-version change, missing rights confirmation, approval, missing entitlement, invalid output, cost-cap breach or disabled kill switch fails closed. Job APIs omit object keys, checksums, raw provider references, deployment data and identities. They expose only the provider-neutral cost-unit result, entitlement state and stable validation code required to review local orchestration. Failure and validation codes cross a shared 1–128-character uppercase alphanumeric/underscore schema; phase-15 D1 triggers apply the same rule to job, job-event and provider-attempt inserts and updates, including an in-place validation pass over existing non-null values. See [Generation pipeline](GENERATION_PIPELINE.md).

## Builds, compatibility and export

Build list reads are bounded to 50 records and never create data. A selected private build ID is retained in component memory and sent only in `X-RigStage-Build-Id` to fixed detail, mutation and export endpoints; it is absent from browser/API URLs, request bodies and route logs. Missing or malformed targets fail before D1, while the resolved workspace remains the first lookup predicate. Staff, admin and owner roles may explicitly create or update a draft with at most one active catalogue part from each of nine categories. Updates use an expected record version and a random server-side mutation token so stale D1 batch statements cannot replace a newer selection. The command bar uses one typed Traditional-Chinese-first contract for workspace and build context, Dashboard navigation, create, the two archive stages and the responsive inspector entry. Viewer rendering omits create and archive controls, but the Worker remains authoritative for every mutation. The Builder's live operation channel separately uses one enumerated bilingual copy contract for create, switch, save, archive and export, with a typed info/success/warning/error tone driving its icon, colour and `status` or `alert` semantics. A valid bilingual public API message may pass through; a monolingual network/parser exception is replaced by bounded operation-specific copy that states whether persisted data, the current selection or a download changed.

Compatibility is calculated at read time from current, verified structured specifications. Six fixed rules cover CPU socket, memory type, motherboard form factor, GPU clearance, cooler clearance and the recorded GPU power-supply recommendation. Missing selections, unverified specifications or absent required fields produce an `unknown` result rather than an inference. The Builder inspector receives only the already workspace-scoped selected part and findings. A typed Traditional-Chinese-first copy module exhaustively maps its tabs, specification-verification states, four finding severities, four asset states and four asset-quality values; known specification and evidence labels show both languages, while an unknown bounded field remains visibly custom instead of receiving a guessed meaning. The component rail separately maps all nine categories plus summary, preserves the existing error/missing/unknown/warning/selected precedence and labels all stock states without treating an unknown count as available. The bottom status bar derives its exhaustive error, unknown, warning or success presentation from the same compatibility summary, in that fail-closed order, and provides bilingual selected-count, workspace-total and action labels. Its responsive icon-only controls retain bilingual accessible names and its export explanation repeats the data-exclusion boundary. Candidate clicks remain local draft state until the existing explicit save mutation. Viewer candidates stay disabled, and the inspector, rail and status bar render no build, part or asset identifier. These client projections do not authorize persistence or export, and visual-asset state never alters a compatibility result.

Portable export is a read-only response and is blocked while any rule is `error` or `unknown`. Schema 2 records the build version and every selected component's current catalogue record version alongside product identity, verified specifications and bilingual rule evidence. This makes later catalogue revisions visible without representing the export as an immutable snapshot or digest. It omits build and workspace IDs, users, pricing, stock, asset metadata, R2 locations and deployment configuration.

The builder may preview only approved selected-component assets. Category scope requests at most one model; summary scope selects at most one model from each of the nine canonical categories and starts those protected private-file reads in parallel. Every remote Blob URL is bound to the scene abort signal, materializes only while that scope is current and is revoked idempotently on abort or release. One failed read does not discard successful peers, and generic partial-failure copy exposes no workspace, asset, parser or object detail. Local development creates an independent synthetic GLB per approved selected component and performs no private read. The shared Three.js preview decodes the bounded set in parallel, disposes successful scenes on scope changes and places them in a separated review grid after display-size normalization. This grid is not a mechanical assembly, physical scale or compatibility result. A typed viewport copy contract exhaustively maps four camera presets, three display modes, ten component steps and four stock states, including authorized private loading, local synthetic preparation, partial or complete failure and missing-model fallback.

## Privacy and observability

Logs contain request method, path, status, duration, request ID and stable error code only. They exclude JWTs, cookies, email addresses, prompts, provider responses and private object locations.

Tracked Wrangler configuration is a non-operational template. Actual deployment coordinates and secrets stay in an ignored mode-`0600` local config or Cloudflare's secret store. Remote migration and deployment processes capture bounded Wrangler stdout／stderr and emit only generic status, so Worker, D1, R2, Workflow, route and version coordinates do not enter normal build logs. Wrangler telemetry and dependency instrumentation are disabled.

Payment remains outside the active request path. The generation credit tables are an entitlement state machine only and cannot accept money, create an order or prove payment. The public repository contains a provider-neutral disabled payment interface only; it has no route, UI, binding, payment ledger or credential. See [Payment boundary](PAYMENT_BOUNDARY.md).

## Frontend

The application uses feature-oriented React modules. The public landing route sits outside `SessionProvider`, so it cannot trigger a protected session read. Its header, hero, three workflow narratives, three merchant use cases, synthetic screenshot alternatives and captions, trust boundary and final sign-in section use typed Traditional-Chinese-first copy; links stay within same-origin entry/demo roots, section anchors and tracked local synthetic images. This public projection contains no workspace target or protected identifier. Dashboard, member management, activity, catalogue, review and builder routes mount the session gate before rendering workspace content. The member and activity pages key asynchronous state to the verified workspace, keep private IDs out of visible copy, and expose management controls or records only for roles the server can authorize. Both pages send private next-page cursors only through fixed protected headers, abort stale page requests, retain the existing projection after a recoverable failure and disable conflicting controls while appending results. The builder route is lazy-loaded so the general shell does not require its code before navigation; Three.js is loaded only when one or more approved GLB resources are ready for decode. The responsive Builder inspector drawer is isolated from page orchestration and reuses the same already scoped inspector projection. It provides labelled modal semantics, initial focus, a Tab boundary, Escape close, background scroll locking and focus restoration without fetching or persisting data. Production dashboard, member, activity, catalogue, review and builder states use protected APIs, while local development uses explicit synthetic fixtures. Semantic controls, visible focus states, responsive layouts and reduced-motion rules are part of the shared design system.
